# Coffee_RAG Agent Instructions

這份規則只套用於 `Coffee_RAG/` 內的 Markdown 知識庫。

## 目標

建立一套可讀、可維護、可轉成 RAG 語料的 Coffee Knowledge Base。

## 基本假設

- 主要語言使用繁體中文。
- 所有知識內容、索引、模板、任務清單都使用 Markdown。
- 每篇檔案只處理一個主題，避免把多個主題混在同一篇。
- 不確定的內容保留為草稿，不補想像出來的細節。
- 新增、移動、重新命名內容後，必須同步更新 `_index.md`。

## 檔名規則

- 一般文章：`001_主題名稱.md`
- QA：`001_問題關鍵字.md`
- FAQ：`001_短問題.md`
- 圖片素材：`001_圖片主題.md`
- 影片素材：`001_影片主題.md`
- 案例：`001_案例名稱.md`
- 產品知識：`001_產品或來源名稱.md`
- 來源資料：`001_來源名稱.md`

檔名使用中文可讀名稱，避免空白。必要時用底線。

## Frontmatter

一般文章使用：

```yaml
---
title:
category:
tags: []
status: draft
updated: 2026-06-30
sources: []
---
```

狀態只使用：

- `draft`: 草稿，內容尚待補齊或查證。
- `review`: 已整理，需要人工確認。
- `ready`: 可納入正式知識庫。

## 來源規則

- 不要編造來源。
- 若沒有來源，`sources: []` 並在 `## 來源` 寫 `待補`。
- 若使用網頁、書籍、影片、訪談、內部文件，必須在 `sources` 與 `## 來源` 留下可追溯資訊。
- 若內容是推論，清楚標示「推論」或「待驗證」。
- 涉及價格、法規、平台規則、最新趨勢、設備規格時，必須先查證最新資料。
- 涉及庫存、供貨狀態、包裝規格、產品頁更新時間時，必須先查證最新資料。

## RAG 寫作規則

- 每段盡量短，讓檢索切分後仍可理解。
- 標題要清楚，不用詩意標題。
- 同義詞放在 `tags` 或「相關概念」中。
- 重要定義放在文章前半部。
- 避免只寫「如上所述」這類離開上下文就失效的句子。
- 內部連結用相對路徑。

## 自動執行流程

當使用者要求新增或整理內容時：

1. 先讀取本檔、`README.md`、`_index.md`、`_queue.md`。
2. 判斷任務屬於哪個資料夾與哪種模板。
3. 只修改任務需要的檔案。
4. 新增文章時使用 `_templates/` 的格式。
5. 更新 `_index.md`。
6. 必要時更新 `_queue.md` 狀態。
7. 檢查檔名、frontmatter、標題、內部連結。
8. 回報新增、修改、待確認事項。

## 建議給 Codex 的指令格式

```text
請依照 Coffee_RAG/AGENTS.md 執行：
任務：[你要做的事]
範圍：[資料夾或主題]
深度：[草稿 / 可發布 / RAG-ready]
來源：[我提供的資料或允許你查證]
```

範例：

```text
請依照 Coffee_RAG/AGENTS.md 執行：
建立 02_產區 的初版內容。
範圍：衣索比亞、哥倫比亞、巴西、瓜地馬拉。
深度：草稿。
完成後更新 _index.md。
```
